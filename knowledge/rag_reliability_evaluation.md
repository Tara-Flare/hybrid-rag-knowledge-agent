# RAG 可靠性与评测体系

## 一、为什么 RAG 需要可靠性机制

RAG 通过检索外部知识，为大语言模型提供回答依据。

但是，检索到相关文档并不代表模型一定能够正确回答。

检索系统可能召回错误文档，也可能只召回部分证据。

即使证据正确，大模型仍然可能生成证据没有支持的内容。

因此，可靠的 RAG 系统需要分别检查检索质量、证据充分性和回答忠实度。

## 二、Answerability：证据充分性判断

Answerability 判断当前检索证据是否足以回答用户问题。

例如，用户问某项政策在2027年的具体规定，但知识库只有2026年的政策。

即使检索结果与政策主题高度相关，也不能据此回答2027年的具体规定。

Answerability 应当判断证据不足，并允许系统拒答。

判断依据应当包括问题中的关键条件、时间、对象和所需事实是否得到证据支持。

检索相似度高，不等于证据充分。

## 三、Grounding：回答依据校验

Grounding 关注模型生成的事实能否由提供的证据支持。

例如，知识库只说明 max_steps 用于限制 Agent 的最大模型决策轮数。

如果模型进一步声称 max_steps 能提高50%的推理速度，这个新增结论就没有得到证据支持。

Grounding 的目标是发现回答中缺少证据支撑的事实。

系统可以根据校验结果选择重新生成、删除无依据内容或拒绝回答。

## 四、生成前与生成后的可靠性检查

生成前主要检查证据质量。

例如，过滤不属于当前知识库的文档，判断候选内容是否足以回答问题。

生成后主要检查回答质量。

例如，将回答拆分为事实性陈述，验证每个陈述是否得到证据支持。

这两个阶段不能互相替代。

生成前证据正确，仍然可能发生模型幻觉。

生成后校验也不能修复完全没有检索到正确资料的问题。

## 五、原子事实拆分

一个模型回答可能包含多个独立事实。

例如：

Agent 可以通过 max_steps 限制最大模型决策轮数，并通过滑动窗口减少历史 Token 消耗。

这句话至少包含两个事实：

第一，max_steps 用于限制模型决策轮数。

第二，滑动窗口可以减少历史 Token 消耗。

如果仅对整句话进行一次判断，容易忽略其中某个事实没有依据。

因此，Grounding 评测可以先将回答拆分为 Atomic Claims，再逐条进行验证。

## 六、事实支持状态

事实验证器可以采用三类状态。

Supported 表示证据明确支持该事实。

Unsupported 表示现有证据不能支持该事实，包括与证据矛盾的情况。

Uncertain 表示证据或表达存在歧义，无法可靠判断。

实际实现时，应区分证据缺失和明确矛盾，因为两者的错误原因不同。

不能把模型给出的支持判断直接视为绝对正确，还需要使用人工标注样本进行核验。

## 七、Faithfulness 指标

Faithfulness 用于衡量回答中的事实有多少得到了证据支持。

一种简单定义是：

Faithfulness = Supported Claims / Total Evaluated Claims

例如，一个回答包含四个原子事实，其中三个得到证据支持，则对应分数为0.75。

如果系统使用 Uncertain 标签，还需要明确这些事实如何计入分母。

不同计分规则不能直接混合比较。

如果模型拒绝回答且没有提出事实性陈述，不应简单地将其 Faithfulness 设为1.0。

拒答质量应该由独立指标评估。

## 八、检索指标与生成指标的区别

Hit@K 用于判断前K个检索结果中是否包含预先标注的正确证据。

MRR 用于衡量第一个正确证据在检索列表中的排名。

这两个指标评价的是检索模块。

Faithfulness 评价的是生成回答与证据的一致性。

Answerability Accuracy 可以评价系统是否正确判断证据足够或不足。

因此，检索效果好并不保证最终回答忠实。

回答忠实也不代表系统检索到了所有相关证据。

## 九、无答案问题与拒答评测

评测集不应该只包含知识库能够回答的问题。

还需要包含知识库没有答案、证据不完整、时间条件不匹配和问题前提错误等场景。

例如，知识库没有说明某个错误类继承自哪个 Python 异常类。

系统不应该根据名称猜测其继承关系。

合理的行为是明确说明证据不足。

拒答评测需要同时统计正确拒答和错误拒答，避免系统通过拒绝所有问题获得表面上的安全性。

## 十、来源引用与真实证据支持

RAG 回答可以附带文件名和 Chunk ID，帮助用户追溯来源。

但是，引用某个 Chunk 不等于该 Chunk 真正支持回答。

如果回答包含三个事实，只引用一个与主题相关但内容不充分的 Chunk，仍然可能存在幻觉。

因此，来源引用需要与具体事实建立支持关系。

来源过滤还需要确保返回的 Chunk 属于当前选定的知识库。

## 十一、Rerank 评测与成本分析

Rerank 可以改变候选文档的排列顺序，但不保证每个问题都会得到改善。

评测时应固定语料、Gold Chunk、问题集和候选召回配置。

分别测试不使用 Rerank 和使用 Rerank 的情况。

除了 Hit@K 和 MRR，还需要统计延迟、模型调用次数及 Token 消耗。

如果排序质量改善有限，但延迟明显增加，就需要分析是否值得默认开启 Rerank。

## 十二、评测集划分与结果复现

开发集用于发现错误、修改代码和调整参数。

回归集用于保证修复的问题不会再次出现。

留出评测集用于在配置确定后，独立衡量最终效果。

如果根据留出评测题反复调整 Prompt 或检索参数，这组题就不再是严格意义上的未见测试数据。

每次正式实验应记录模型版本、索引版本、切块参数、检索配置和评测数据版本。

评测结果必须由程序实际运行得到，不能根据预期效果填写指标。

## 十三、可靠性机制的局限

Answerability 判断可能出现误判。

Grounding 验证器也可能错误地把无依据事实标记为 Supported。

少量测试问题的高分不能证明系统在复杂企业知识库中同样可靠。

因此，可靠性建设需要结合人工标注、自动化测试、失败案例分析和持续评测。

可靠 RAG 的目标不是完全消除所有错误，而是让错误可以被发现、量化、定位并持续改进。
