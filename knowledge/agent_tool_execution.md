# Agent 工具调用与错误处理

## 一、Function Calling 的工作原理

Function Calling 允许大模型以结构化形式请求外部工具，但大模型本身不会执行 Python 函数。

模型负责根据用户问题和工具描述，选择工具名称并生成参数。

Python Runtime 负责解析参数、检查合法性、执行真实函数，并将执行结果返回给模型。

例如，用户要求计算两个数字的乘积，模型可以请求 calculator 工具，Python 执行计算后，再由模型生成最终回答。

## 二、Tool Schema 与工具注册表

Tool Schema 是提供给模型的工具接口描述，通常包括工具名称、功能说明、参数类型和必填字段。

工具注册表则是 Python 程序中工具名称与可执行函数之间的映射。

Tool Schema 解决模型如何知道工具可以做什么的问题。

工具注册表解决 Python 如何找到实际执行函数的问题。

模型生成的工具名称不能直接作为任意 Python 代码执行，必须经过允许调用的工具注册表进行匹配。

## 三、工具参数校验

模型生成的工具参数通常以 JSON 字符串形式返回。

Runtime 首先需要解析 JSON，并确认参数满足工具接口要求。

例如，calculator 的 expression 参数应该是合法的计算表达式。

如果模型生成了不合法的 JSON、缺少必填参数或者使用不存在的工具名称，系统应该返回明确的参数错误，而不是直接执行。

参数校验是 Function Calling 的重要安全边界。

## 四、max_steps 与 Agent Loop

Agent Loop 允许模型多次决策并调用工具。

例如，模型可以先搜索知识库，再读取文件，最后生成回答。

但如果模型一直请求工具，Agent 可能无法正常结束。

max_steps 用于限制一次任务允许的最大模型决策轮数。

需要注意，max_steps 不一定等于工具调用总次数。

如果一次模型决策返回多个 tool_calls，这一轮可能执行多个工具。

因此，在复杂系统中，还可以分别限制工具调用数量、执行时间和资源消耗。

## 五、tool_call_id 的作用

模型可能在一次响应中请求多个工具。

每个工具请求通常具有独立的调用 ID。

Python 执行工具后，需要将结果与对应的 tool_call_id 关联。

这样模型才能区分不同工具请求的执行结果。

即使某个工具执行失败，也应该为对应的工具调用提供结果消息，说明失败原因。

不能把工具 A 的执行结果错误地关联到工具 B。

## 六、工具失败的分类

工具执行失败可能来自参数错误、权限不足、资源不存在、网络超时或服务暂时不可用。

不同错误需要不同处理策略。

参数错误通常需要修改输入参数，重复执行相同参数没有意义。

资源不存在时，应检查资源标识是否正确。

权限错误通常需要停止执行并向用户说明权限限制。

临时网络超时可能允许有限次数的重试。

是否重试应该由错误类型和具体业务语义共同决定。

## 七、为什么不能盲目重试

对于只读工具，部分临时故障可以安全重试。

但对于具有写入副作用的工具，重试可能造成重复操作。

例如，创建记录或发送请求的操作，如果第一次已经成功但响应丢失，直接重试可能产生重复数据。

因此，写操作通常需要结合幂等机制、请求标识或状态检查进行恢复。

不能简单地对所有异常使用相同的重试次数。

## 八、结构化工具结果

工具执行结果可以统一封装为结构化对象。

成功结果可以包含 success、data 等字段。

失败结果可以包含 error_type、error_message 等字段。

结构化结果便于 Agent 判断执行状态，也便于 FastAPI、日志系统和自动化测试进行处理。

不能仅依靠自然语言中是否出现“失败”来判断操作是否成功。

## 九、异常处理与安全

工具异常不应该直接导致整个 Agent 无限循环。

系统应该记录必要的错误信息，并根据故障类型决定是否继续。

日志可以记录工具名称、执行耗时、成功状态和错误类型。

但向模型或用户返回错误信息时，应该避免暴露密钥、敏感文件路径和内部服务凭证。

错误处理的目标不仅是避免程序崩溃，还包括保持工具调用状态一致、限制风险和提供可追踪的失败原因。
