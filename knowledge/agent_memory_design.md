# Agent 记忆与上下文管理设计

## 一、为什么 Agent 需要记忆

大语言模型每次推理主要依赖当前请求提供的上下文。

如果 Agent 不保存历史信息，用户在下一轮对话中提到“刚才的问题”，模型可能无法理解。

因此，Agent 通常需要管理对话历史，并根据任务选择需要保留的信息。

Agent 记忆并不意味着模型参数发生了变化，而是系统通过外部存储和上下文组织，让模型能够利用历史信息。

## 二、短期记忆

短期记忆主要保存当前会话中的最近对话内容。

例如，用户先询问 RAG 的定义，再询问“它有哪些缺点”，系统需要保留上一轮问题，才能理解“它”指的是 RAG。

短期记忆通常由消息列表管理，包括用户消息、助手回答和工具调用结果。

短期记忆的主要作用是保持多轮对话的连续性。

## 三、长期记忆

长期记忆保存跨会话仍然有价值的信息。

例如，用户的长期学习目标、项目名称和稳定偏好，可以在后续会话中继续使用。

长期记忆通常需要持久化存储，例如 JSON、SQLite 或其他数据库。

长期记忆与短期记忆的区别主要是信息用途、生命周期和读取策略，而不是简单由存储格式决定。

不能因为信息保存在 SQLite 中，就自动认为它属于长期记忆。

## 四、上下文窗口

上下文窗口限制模型单次请求可以处理的 Token 数量。

当历史对话不断增加时，如果把所有消息都发送给模型，可能导致上下文超过限制、延迟增加和 Token 消耗上升。

因此，Agent 需要使用上下文管理策略，控制进入模型的历史信息。

上下文窗口和长期记忆不是同一个概念。

前者描述模型单次请求的上下文容量，后者描述系统如何长期保存和使用信息。

## 五、滑动窗口策略

滑动窗口只保留最近若干轮对话。

例如，Agent 可以只将最近五轮消息发送给模型，避免历史对话无限增长。

滑动窗口实现简单，可以降低上下文长度和 Token 消耗。

但它存在信息丢失的问题：较早的用户要求或重要背景可能被移除。

因此，滑动窗口适合控制短期上下文，但不能完全替代长期记忆。

## 六、对话摘要

对话摘要通过压缩较早的历史消息，保留关键事实和任务进展。

例如，一段很长的项目开发对话，可以被总结为当前开发阶段、已经完成的模块和剩余任务。

摘要能够减少上下文长度，但可能遗漏细节或改变原意。

因此，对话摘要需要关注事实准确性，并避免把不确定信息保存为确定事实。

滑动窗口主要通过删除旧消息控制长度，而摘要通过压缩旧消息保留部分信息。

## 七、基于检索的记忆

当长期记忆数量较多时，Agent 不一定需要读取全部历史信息。

系统可以将历史记录进行索引，并根据当前问题检索相关内容。

例如，用户询问之前讨论过的 RAG 评测方案，系统可以检索相关历史摘要，而不是加载所有对话。

这种方式与 RAG 的检索思想相似，但检索对象是历史记忆而不一定是外部知识库文档。

## 八、Session 会话隔离

Session ID 用于区分不同的对话会话。

不同 Session 应当具有独立的对话状态，避免一个会话中的私人信息被错误加载到另一个会话。

Session 隔离不能只依赖模型提示词，还需要在程序的数据读取和存储逻辑中实现。

例如，查询历史记录时，应根据经过验证的会话标识加载对应数据。

## 九、Session TTL 与并发控制

Session TTL 表示会话状态在一定时间没有活动后可以过期。

TTL 有助于清理长期不用的内存状态，减少资源占用。

但删除内存中的 Session 对象，不一定等于删除磁盘上的持久化历史。

当同一 Session 同时收到多个请求时，还可能出现历史消息更新顺序混乱的问题。

系统可以使用会话级锁，避免同一个会话被多个请求同时修改。

不同 Session 则可以根据服务能力并发处理。

## 十、记忆存储与数据安全

JSON 适合结构简单、读写频率较低的数据。

SQLite 更适合结构化记录、查询和事务管理。

对于需要多人同时使用的系统，还需要考虑数据库并发、访问权限和数据隔离。

记忆系统应避免保存不必要的敏感信息，并提供合理的数据清理机制。

记忆管理的目标不仅是让 Agent 记住更多内容，还包括控制上下文成本、保持信息准确以及保护不同会话的数据边界。
